# Adversarial review findings — round 1

## 1. CRITICAL — the proposed `devTrustHeaders` control does not control header trust

- **Plan claim:** NOR-268 “Task 2: config plumbing” says `devTrustHeaders` is the local-development escape hatch and that its constructor guard prevents production impersonation (`2026-08-01-setup-management-ui.md:699-727`). NOR-267 reiterates that the flag “is what permits header-only auth” (`:3074-3089`).
- **Evidence:** NOR-271 later says the flag “needs no branch” because `parseEasyAuthPrincipal` always reads whatever headers arrive (`:3864-3884`). The only proposed guard rejects `devTrustHeaders && entra`; it does not reject `setupUi.enabled && !entra && !devTrustHeaders`, nor does it make the parser conditional. Consequently, any self-hosted/Docker deployment that enables `setupUi` without `entra` accepts an arbitrary `X-MS-CLIENT-PRINCIPAL-NAME` from the network even though `devTrustHeaders` is false. Merely having `entra` is not proof that EasyAuth is present: in the real server, `RouterServerConfig.entra` configures bearer-token validation for `/enroll` (`packages/router/src/RouterServer.ts:204-214`, `packages/router/src/enrollment.ts:68-113`). The production entrypoint binds the app to `0.0.0.0` (`docker/router/entrypoint.mjs:133-143`).
- **Recommended change:** Make setup authentication an explicit strategy. Refuse startup unless exactly one of (a) a cryptographically verified Entra token mode or (b) an explicit local-dev header mode is selected. The header parser must only be reachable in mode (b). Do not infer “EasyAuth is installed” from the unrelated enrollment `entra` object.

## 2. CRITICAL — Terraform guarantees an initial public impersonation window

- **Plan claim:** One `enable_setup_ui` flag both enables the router routes and attaches EasyAuth, and the auth resource's dependency is described as sufficient ordering (`2026-08-01-setup-management-ui.md:842-875`, `:913-950`, `:953-994`).
- **Evidence:** The Container App must be updated first to add `CYRUS_ROUTER_SETUP_UI_ENABLED`; only afterward can the child `authConfigs` resource be created because `router_auth` explicitly depends on `azurerm_container_app.router` (`:913-950`). During that interval the new revision publicly serves `/setup`, but no auth sidecar is sanitising headers, and finding 1's proposed application code trusts a forged header. The real stack has external ingress on target port 8787 (`infra/azure/terraform/router.tf:69-100`) and the generated config binds Fastify on all interfaces (`docker/router/entrypoint.mjs:133-143`). The trust gate runs only after the whole apply (`2026-08-01-setup-management-ui.md:1007-1047`), so it cannot prevent exploitation of the window.
- **Recommended change:** Split auth infrastructure and route enablement into separately applied flags/stages: first install and verify EasyAuth while `/setup` is absent, then deploy the route. Make rollback reverse that order. A signed-token check in the app would also remove this transient trust gap.

## 3. CRITICAL — `KekKeyId` creates an authenticated SSRF that leaks a Key Vault bearer token

- **Plan claim:** Storing the versioned KEK ID on each Table row makes rotation safe, and `unwrap` should call that stored ID (`2026-08-01-setup-management-ui.md:1125-1142`, `:1234-1247`, `:1408-1426`).
- **Evidence:** `TableSecretStore.getRecord` passes the row's untrusted `KekKeyId` directly to `openBundle` (`:1819-1833`). `KeyVaultKeyWrapper.unwrap` then constructs a URL from that value and sends `Authorization: Bearer <vault token>` before AES-GCM can authenticate anything (`:1408-1426`). A writer who changes `KekKeyId` to `https://attacker.example/...` receives a token scoped to `https://vault.azure.net/.default`. This is an escalation from Table write access to the router identity's Key Vault permissions, which include existing Secrets User/Officer roles in the real stack (`infra/azure/terraform/main.tf:133-147`) plus the proposed Crypto User role. The existing `KeyVaultSecretStore` avoids this class by constructing every URL from its configured, fixed `vaultUrl` (`packages/router/src/KeyVaultSecretStore.ts:59-65`, `:72-95`, `:98-124`). GCM AAD cannot help because the network request occurs before authentication.
- **Recommended change:** Never fetch an arbitrary stored URL. Parse and validate that the stored key identifier has exactly the configured HTTPS origin, key name, and a valid version segment; preferably store only the version and construct the URL from the configured vault/key. Verify Key Vault's echoed `kid` against that allowlist as well. Add a test proving a hostile `KekKeyId` causes no network request and no token-provider call.

## 4. HIGH — needs verification: the EasyAuth trust claim is broader than Microsoft's guarantee and the live test covers only one ingress path

- **Plan claim:** D1 treats header stripping as the “load-bearing security property” and says `AllowAnonymous` is safe because the sidecar strips client-supplied identity headers (`2026-08-01-setup-management-ui.md:82-85`, `:383-396`).
- **Evidence:** Microsoft's [Container Apps authentication documentation](https://learn.microsoft.com/en-us/azure/container-apps/authentication) does support the narrower statement that **external** requests cannot set the injected headers and says authenticated requests still receive identity headers under Allow Anonymous. It does not document whether the same sanitisation is guaranteed for app-name/internal-FQDN traffic, WebSocket upgrades, or direct within-replica access to the target port. The real application exposes the `/device` upgrade by attaching `WebSocketServer` directly to Fastify's raw HTTP server (`packages/router/src/RouterServer.ts:440-447`, `packages/router/src/DeviceGateway.ts:49-55`), and the ACA process listens on `0.0.0.0` (`docker/router/entrypoint.mjs:133-143`). The proposed test only curls the public FQDN (`2026-08-01-setup-management-ui.md:1035-1047`); before NOR-271 it is only a 404 and proves nothing about principal parsing. This does not establish a bypass, but it leaves the whole trust boundary unverified.
- **Recommended change:** Treat every non-public path as **needs verification** and test from another Container App in the environment, after a forced WSS reconnect, and—if the platform permits another container in the replica—against the target port directly. Prefer verifying a signed ID token in application code for `/setup` instead of making undocumented proxy topology a credential boundary. Verify that ACA actually supplies `X-MS-TOKEN-AAD-ID-TOKEN` for this flow before naming token-store fallback as a contained solution.

## 5. HIGH — auto-provisioning is enabled before the plan establishes an enforceable user allowlist

- **Plan claim:** First sign-in safely auto-provisions because the user passed EasyAuth, the email-domain check, and an Entra app configured with “Assignment required” (`2026-08-01-setup-management-ui.md:152-156`, `:2266-2273`).
- **Evidence:** Assignment is only “recommended,” not a prerequisite (`:810-818`). The shown command turns on `appRoleAssignmentRequired` but never performs the promised Cyrus-users group assignment. The proposed `authConfigs` has no `defaultAuthorizationPolicy.allowedPrincipals.groups` restriction (`:919-946`). Microsoft documents that, by default, any tenant user can request a token and that group assignment is a separate operation ([ACA authentication](https://learn.microsoft.com/en-us/azure/container-apps/authentication), [Entra app assignment](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-user-or-group-access-portal)). `autoProvisionUsers` defaults true (`:867-871`) and `allowedDomain` is optional. The design also uses mutable/reassignable email as the authorization and storage identity while merely logging `objectId`; the real database is keyed by case-insensitive email (`packages/router/src/RouterStore.ts:7-13`) and the proposed Table key is derived from email. A UPN rename creates a new user/secret identity; email reuse can attach a different Entra object to old state.
- **Recommended change:** Make group/user assignment an explicit, verified prerequisite to enabling the UI, with the actual Graph/CLI assignment command or an authConfig allowed-principals policy. Default auto-provisioning off until that check passes. Persist and authorize by `(tenantId, oid)` and treat email as mutable display/routing metadata, with a deliberate migration for existing email-keyed records.

## 6. HIGH — the hand-written Table REST client omits required protocol details and encodes `UpdatedMs` with the wrong OData type

- **Plan claim:** Setting the storage scope, `x-ms-version`, `DataServiceVersion`, and JSON content type is sufficient; `UpdatedMs` is an `int64` (`2026-08-01-setup-management-ui.md:106-108`, `:1125-1136`, `:1735-1746`, `:1939-1956`).
- **Evidence:** The proposed request supplies `DataServiceVersion` but not `MaxDataServiceVersion` (`:1945-1955`). Microsoft's Table REST documentation says Table calls require the OData version headers and documents compatible `DataServiceVersion`/`MaxDataServiceVersion` pairs ([OData version headers](https://learn.microsoft.com/en-au/rest/api/storageservices/setting-the-odata-data-service-version-headers)); the Update/Insert-or-Replace operation docs also list `Date` or `x-ms-date` as required ([Update Entity](https://learn.microsoft.com/en-us/rest/api/storageservices/Update-Entity2), [Insert Or Replace Entity](https://learn.microsoft.com/en-us/rest/api/storageservices/insert-or-replace-entity)). Whether `Date` is waived for bearer-authenticated Table requests is unclear from the OAuth sample and **needs verification**. More definitively, JSON `Edm.Int64` requires an `@odata.type: "Edm.Int64"` annotation and a string value; a bare JavaScript number is not the promised int64 ([Table payload format](https://learn.microsoft.com/en-us/rest/api/storageservices/payload-format-for-table-service-operations)). All proposed tests mock `fetch`, so none detects an Azure 400. Key Vault base64url and the two OAuth scopes are correct, but the current Key Vault docs redirect a requested 7.4 crypto reference to the current API, so continued 7.4 support for `wrapkey`/`unwrapkey` also needs a live check.
- **Recommended change:** Implement the complete documented header set, encode `UpdatedMs@odata.type = "Edm.Int64"` with a decimal string (or use a DateTime), and add a disposable real-Azure integration smoke for GET, insert, conditional update, 412, wrap, and unwrap. Keep mocked unit tests, but do not use them as API-contract proof.

## 7. HIGH — the proposed point GET suppresses the ETag, so normal writes are unconditional

- **Plan claim:** One entity plus ETag makes record creation/update atomic and concurrent edits detectable (`2026-08-01-setup-management-ui.md:89-93`, `:1880-1893`, `:1896-1917`).
- **Evidence:** `getRecord` requests the point entity as `Accept: application/json;odata=nometadata` and reads the ETag only from `response.headers.get("etag")` (`:1805-1822`). Azure's [Query Entities](https://learn.microsoft.com/en-us/rest/api/storageservices/query-entities) response-header contract does not list an `ETag` header, and its [payload-format documentation](https://learn.microsoft.com/en-us/rest/api/storageservices/payload-format-for-table-service-operations) says `odata.etag` is included with full metadata but not with no/minimal metadata. The planned normal GET therefore produces `etag: ""`. The request helper emits `If-Match` only for a truthy value (`:1945-1955`), so the subsequent PUT is an unconditional upsert and the advertised 412 path cannot occur. The absent case separately races: two callers can both observe 404 and then issue unconditional PUTs.
- **Recommended change:** Fetch full metadata and parse/validate `odata.etag` (or use another documented ETag retrieval mechanism verified against Azurite and live Azure); fail closed if an existing entity has no ETag. Use Insert Entity (`POST`) for the absent case and translate `EntityAlreadyExists`/409 into the conflict flow. Add normal-update, missing-ETag, and concurrent-create tests.

## 8. HIGH — the UI's ETag is read at save time, so the advertised two-tab conflict detection does not work

- **Plan claim:** Two tabs loaded concurrently will make the second save return 409, and this is a manual acceptance criterion (`2026-08-01-setup-management-ui.md:4494-4504`, `:5052-5065`).
- **Evidence:** `SetupPageModel` contains no ETag/version (`:3023-3030`). `POST /setup/save` calls `getRecord(email)` only when the save request arrives and immediately writes with that freshly read ETag (`:4941-4958`, `:4981-4986`). If tab A saves and then tab B saves, tab B reads A's current ETag and overwrites A successfully. A 412 can occur only if another write lands in the tiny interval between B's server-side GET and PUT, not because B rendered a stale page. The proposed test manufactures a conflict inside a fake store (`:4865-4874`) and therefore does not test the stated two-tab behavior.
- **Recommended change:** Capture the record ETag/version when rendering the page and submit an opaque, integrity-protected version token bound to the principal. Use that page-load version for the conditional write. Add a sequential browser/integration test: render A, render B, save A completely, then save B and require 409.

## 9. HIGH — the migration command cannot discover both its source and destination in the documented runbook state

- **Plan claim:** `cyrus router secrets migrate` reads the configured Key Vault and writes the Table before `containers.tableStore` is added to config (`2026-08-01-setup-management-ui.md:2066-2088`).
- **Evidence:** The command has no endpoint, table, or KEK arguments (`:2070-2076`). The runbook deliberately keeps `tableStore` out of `CYRUS_ROUTER_CONTAINERS_JSON` until after migration (`:2082-2085`), so the CLI has no target configuration. In the real CLI, `openSecretStore()` selects exactly one backend from the current config (`apps/cli/src/commands/RouterCommand.ts:407-415`), and the current config contains only `keyVaultUrl` (`infra/azure/terraform/router.tf:13-24`). Once `tableStore` is enabled, the proposed precedence makes `openSecretStore` return Table and loses the source. The promised “reuse” is also impossible as stated: `KeyVaultSecretStore.listForEmail` is private and requires an already-known email (`packages/router/src/KeyVaultSecretStore.ts:137-163`), whereas migration claims it will discover every tagged user. The real secrets dispatcher has no migration case or source/target injection seam (`apps/cli/src/commands/RouterCommand.ts:1111-1127`).
- **Recommended change:** Always render a distinct migration target configuration while keeping a separate active-backend selector, or require explicit source/target arguments. Add a public, tested Key Vault enumeration API that paginates all tagged records and groups them by email. Give `RouterCommand` injectable backend factories so its unit tests do not reach Azure.

## 10. HIGH — leaving Key Vault untouched is not a rollback after the first Table write

- **Plan claim:** Keeping old Key Vault secrets for one week is a rollback path (`2026-08-01-setup-management-ui.md:2080-2088`).
- **Evidence:** After cutover, both the UI and break-glass CLI select Table first (`:2030-2060`). Any new user, new variable, deletion, or credential rotation exists only in Table. Rolling the config back to Key Vault restores the stale migration-time snapshot and can inject revoked credentials or omit new ones. This matters immediately because the real router reads the selected backend during `ContainerTargets.buildEnv` (`packages/router/src/RouterServer.ts:498-567`, `packages/router/src/ContainerTargets.ts:443-483`), and `CLAUDE.md:459-468` records create-from-image credential semantics.
- **Recommended change:** Define a real rollback mechanism: dual-write during a bounded cutover (with surfaced partial failures), a write freeze plus explicit reverse migration, or an audited Table-to-Key-Vault export before rollback. Verify counts/hashes and two user bundles in both directions. Document rollback for every flag transition, not merely data retention.

## 11. HIGH — the default-executor migration cannot recover historical explicit-device intent

- **Plan claim:** Shipping an explicit `{"type":"device"}` sentinel plus an `EXECUTOR` column and pre-flight safely prevents existing device users from being captured by `defaultExecutor: "aca"` (`2026-08-01-setup-management-ui.md:2738-2745`, `:2869-2918`, `:2940-2949`).
- **Evidence:** The plan correctly admits that historical explicit device and never-configured are the same SQL NULL. The real CLI writes NULL for device (`apps/cli/src/commands/RouterCommand.ts:827-853`), and `RouterStore.getUserExecutor` collapses both missing row values and NULL to `undefined` (`packages/router/src/RouterStore.ts:942-955`). `listUsers` does not expose `executor_json` (`:374-395`). No new column or code can retrospectively determine which NULLs were deliberate. The runbook's “note anyone showing device” therefore either selects every NULL user or guesses; its later expectation that “previously blank” users become ACA contradicts pinning all of them.
- **Recommended change:** Preserve NULL's historical meaning as device. Introduce an explicit `{"type":"default"}`/inherit sentinel for users that should follow the router default, and write it for newly auto-provisioned users. Migrate existing users only from an operator-supplied allowlist or another authoritative source; do not claim an automatic pre-flight can infer intent.

## 12. HIGH — HTMX will not render the planned 400/403/409 error fragments

- **Plan claim:** Mutation routes return 400/403/409 HTML fragments containing fresh CSRF tokens and visible error/conflict banners (`2026-08-01-setup-management-ui.md:4181-4238`, `:4242-4301`, `:4850-4874`, `:4996-5004`).
- **Evidence:** HTMX 2's default response handling does not swap 4xx/5xx responses; it raises an error instead. This is explicit in the [HTMX response-handling documentation](https://htmx.org/docs/#response-handling). The proposed page includes no `htmx.config.responseHandling`, `htmx:beforeSwap` handler, or response-target extension (`:3377-3399`). Fastify injection tests assert status/body only, so they pass while the browser leaves the old fragment and old CSRF token in place.
- **Recommended change:** Configure and test response handling for the selected status codes (for example, allow swaps for 400/403/409), use a supported 422 policy, or return 200 for application-level form errors while preserving semantic state in the fragment. Add browser-level tests for invalid name, expired CSRF, and ETag conflict.

## 13. HIGH — the readiness banner is outside the only swap target and can never update after a mutation

- **Plan claim:** Re-rendering the whole `#variables` fragment keeps the client consistent, and saving the missing required value clears the “not ready” banner (`2026-08-01-setup-management-ui.md:3037-3038`, `:4838-4842`).
- **Evidence:** `renderPage` places `renderMissingBanner` before `renderVariablesTable` (`:3368-3396`). Every mutation response contains only `renderMessage(...) + renderVariablesTable(...)` and targets `#variables` (`:4286-4301`, `:4559-4575`). Therefore a banner present on initial load remains after required values are set, and no banner appears when a required value is cleared. The proposed save test merely asserts that the response body lacks “not ready”; it does not inspect the resulting DOM.
- **Recommended change:** Put readiness state inside the swapped container or send an HTMX out-of-band replacement for a stable banner element. Test the DOM after both setting and clearing a required value.

## 14. HIGH — the dependency graph is internally false

- **Plan claim:** NOR-271 “only needs NOR-268's `parseEasyAuthPrincipal`” and deliberately decouples the UI chain from Table/bootstrap (`2026-08-01-setup-management-ui.md:113-125`, `:3068-3072`).
- **Evidence:** NOR-271 explicitly says it consumes `SetupBootstrap` from NOR-270 (`:3119-3128`), makes it a required `SetupRouteDeps` member (`:3039-3055`, `:3731-3739`), calls it on every GET (`:3793-3806`), and dereferences `this.setupBootstrap!` during route registration (`:3864-3879`). NOR-270 in turn explicitly consumes NOR-269's `ensureRecord` (`:2231-2234`). As written, the real critical path is 268 + 269 → 270 → 271 → 272 → 273, not the diagram or staffing guidance.
- **Recommended change:** Correct the dependencies and critical path, or actually decouple NOR-271 by defining a bootstrap interface/fallback in that issue that does not depend on NOR-270/Table. Do not assign engineers based on the current graph.

## 15. HIGH — the production regression gate does not perform the WSS reconnect or webhook test it claims

- **Plan claim:** Post-apply smoke verifies `/healthz`, machine routes, a worker WSS reconnect, and thus mitigates the all-path blast radius of `authConfigs` (`2026-08-01-setup-management-ui.md:127-132`, `:1014-1033`).
- **Evidence:** The WSS step only runs `cyrus router containers list` and observes an already-connected worker (`:1028-1031`); it never disconnects or reconnects anything. A socket established before the auth change proves nothing about a new upgrade. The real WSS server attaches after listen directly to `/device` and authenticates only after a `hello` frame (`packages/router/src/RouterServer.ts:440-447`, `packages/router/src/DeviceGateway.ts:204-234`). Likewise, an unsigned empty POST that yields any application 4xx proves only “not 302,” not that a genuine signed Linear webhook is accepted and routed. The repo invariant explicitly treats WSS heartbeat state as liveness, not infrastructure status (`CLAUDE.md:459-468`).
- **Recommended change:** Force one worker connection closed and prove a new `hello`/heartbeat reaches connected state; verify queued-event delivery after reconnect. Send a real or faithfully signed webhook and observe routing. Run these on a staged revision before shifting production traffic, and include `/enroll`, artifacts, teardown callback, and workspaces auth checks.

## 16. MEDIUM — D3 materially overstates Azure Table capacity for the chosen one-string ciphertext schema

- **Plan claim:** The 1 MiB entity and 64 KiB/property limits are “far above any realistic env-var set” (`2026-08-01-setup-management-ui.md:89-93`).
- **Evidence:** Azure Table strings are UTF-16 and limited to 64 KiB—about 32K characters or less ([Table data model](https://learn.microsoft.com/en-us/rest/api/storageservices/understanding-the-table-service-data-model#property-types)). `Ciphertext` is one base64 string (`:1125-1136`), so its practical encrypted payload ceiling is roughly 24 KiB before JSON/base64 overhead, not 1 MiB. The form parser accepts 64 KiB of URL-encoded input (`:3531-3564`) and the backend performs no post-serialization size check, so the UI can accept data that predictably fails at storage with `PropertyValueTooLarge`.
- **Recommended change:** Define and enforce a bundle byte limit before wrapping/writing, with an error the UI can display. Test boundary and multi-byte values. If larger bundles are legitimate, use a binary property/chunked properties or a different storage layout rather than citing the entity limit.

## 17. MEDIUM — all new Azure calls are unbounded and have no transient-error policy

- **Plan claim:** Hand-rolled `fetch` is an adequate production implementation because it matches existing code and has injectable test seams (`2026-08-01-setup-management-ui.md:101-108`).
- **Evidence:** Neither `KeyVaultKeyWrapper.crypto` nor `TableSecretStore.request` supplies an abort signal, deadline, retry, `Retry-After` handling, or client request ID (`:1413-1433`, `:1939-1971`). A stalled Table read blocks setup and container environment construction indefinitely; a stalled wrap/unwrap blocks every secret mutation/read for that user. Existing `StateBackup` is not a sufficient precedent—it also calls bare fetch (`packages/router/src/StateBackup.ts:54-68`, `:126-150`), while the repository explicitly records that Node fetch has no deadline and unbounded Azure calls can hold critical slots (`CLAUDE.md:468`).
- **Recommended change:** Add configurable request deadlines with `AbortSignal`, correlation IDs, and bounded retries for 408/429/5xx that honor `Retry-After`; never retry 412 blindly. Test timeout, abort, throttling, and that errors do not degrade to an empty bundle.

## 18. MEDIUM — the CSRF design is mislabeled, leaks tokens into URLs, and excludes a state-changing GET

- **Plan claim:** `CsrfTokens` is a “double-submit” design and every mutating route is CSRF-protected (`2026-08-01-setup-management-ui.md:3060-3066`, `:3474-3485`, `:3981-4095`).
- **Evidence:** There is no second CSRF cookie to compare, so this is a stateless signed synchronizer token, not double-submit. DELETE sends the eight-hour token in the query string (`:4085-4095`, `:4312-4318`), exposing it to server/proxy access logs, diagnostics, and developer tooling unnecessarily. More importantly, `GET /setup` calls `bootstrap.ensure`, which creates a SQLite user and Table record (`:3611-3619`, `:3793-3806`), despite the “read-only page” claim (`:3133-3135`) and without CSRF. A cross-site navigation can trigger auto-provisioning for an already signed-in tenant user.
- **Recommended change:** Describe the mechanism accurately, send CSRF in a form body or `X-CSRF-Token` header, and bind it to the stable principal ID as well as email. Move first-time provisioning to an explicit authenticated POST with CSRF, or document and threat-model why cross-site idempotent provisioning is acceptable.

## 19. MEDIUM — `enable_setup_table` is not reversible despite being presented as a feature flag

- **Plan claim:** Storage creation and backend selection are independent, flag-gated blast radii, and disabled defaults are harmless (`2026-08-01-setup-management-ui.md:98-99`, `:2143-2164`, `:2199-2204`).
- **Evidence:** The KEK resource uses `count = var.enable_setup_table ? 1 : 0` and `lifecycle.prevent_destroy = true` (`:2107-2124`). Changing the flag from true back to false asks Terraform to destroy a protected resource and fails the plan/apply. The Table itself, role assignments, and potentially all ciphertext are also count-controlled. Thus the infrastructure flag is one-way, while the plan supplies no decommission/state-removal procedure.
- **Recommended change:** Keep the KEK/Table resources persistent once created and use only the backend-selector flag for rollback. If teardown is required, provide an explicit, gated decommission workflow that exports/verifies data, disables the backend, retires key versions, and deliberately removes resources/state.

## 20. MEDIUM — the proposed `secretBackendKind` test seam does not compile under this repository's TypeScript settings

- **Plan claim:** Add a `readonly secretBackendKind` field and assign it inside `buildContainerTargets` (`2026-08-01-setup-management-ui.md:1984-2009`, `:2030-2055`).
- **Evidence:** TypeScript readonly instance properties may only be assigned in the constructor/initializer, not from an ordinary method. `buildContainerTargets` also returns immediately when `containers` is absent in the real code (`packages/router/src/RouterServer.ts:498-503`), leaving a non-optional field uninitialized. The repo enables `strict`, `noUnusedLocals`, and `noImplicitReturns` (`tsconfig.base.json:1-20`). The proposed field therefore creates both readonly-assignment and strict-initialization errors unless its declaration differs from the plan.
- **Recommended change:** Have `buildContainerTargets` return a structured result containing `{ service, secrets, kind }` and assign readonly fields directly in the constructor, or make the diagnostic getter derive from config. Add tests for no-containers, file, Key Vault, and Table cases.

## 21. MEDIUM — config plumbing misses an entrypoint gate and the documented local recipe cannot start

- **Plan claim:** Mapping three new setup env vars, widening Zod, and adding a containers guard completes config plumbing; NOR-271 is locally demoable with the grouping issue's recipe (`2026-08-01-setup-management-ui.md:670-780`, `:2632-2676`, `:3074-3087`).

The later NOR-271 recipe includes containers, so the plan gives two incompatible instructions.
- **Recommended change:** Add every new env var to `anyProvided`, test regeneration from each one (including an existing config file), and keep one canonical local recipe that satisfies the final schema/constructor invariants.

## 22. LOW — planned view tests and the optional-clear contract contradict their own implementation

## 23. LOW — “values never travel to the browser” is an unsafe overstatement

- **Plan claim:** D5 says values never travel to the browser and this makes the page safe to leave open (`2026-08-01-setup-management-ui.md:95-96`, repeated at `:5041-5044`).
- **Evidence:** The narrower implementation property is that **stored values are never returned in a response**. New secrets are necessarily typed into browser DOM, handled by htmx, and sent in request bodies (`:3333-3346`, `:4786-4812`). They remain observable to browser extensions, developer tools, compromised client JavaScript, password managers, and any request-body logging. `autocomplete="off"` is advisory, not a security boundary. The planned browser check searches response bodies only (`:5052-5058`).
- **Recommended change:** Replace the claim everywhere with “stored values are never returned/displayed.” Add an explicit no-request-body-logging rule, review browser/password-manager autocomplete behavior, keep the strict same-origin CSP, and include request/DOM exposure in the user-facing threat model.
